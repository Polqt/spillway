# 14. v0.5 difficulty routing and evaluation gates

Date: 2026-10-15
Status: accepted

## Context

v0.5 adds optional difficulty selection to `auto` and evaluates whether it reduces estimated cost without unacceptable latency, quality, or correctness regressions.
Current `auto` routing, capability checks, quota handling, budget handling, spillover, and the public `x-spillway-route` header are established contracts (ADRs 0006, 0007, 0008, and 0010).
The implementation needs explicit rule semantics and evaluation gates before runtime behavior is added.

## Decision

- Stage 1 rules are user-defined only; there is no implicit built-in matching ruleset.
- Difficulty is one of the closed labels `simple`, `moderate`, or `hard`.
  Rules are evaluated in configuration order and the first match wins.
  If no rule matches, the difficulty is `moderate`.
- Each difficulty maps to a non-empty ordered list of tier names already in `router.auto`.
  That list is the full fallback order for the difficulty; candidates repeated across its tiers are de-duplicated by first occurrence so a candidate is attempted at most once per request (ADR 0006).
  Exhausting its tiers returns the existing no-candidate error; routing does not silently change the selected difficulty.
- Tier order must retain zero-spend tiers before tiers that allow spending.
  Every candidate remains subject to current capability and context-window filtering, quota and budget checks, and spillover policy.
  A budget-blocked candidate is skipped under ADR 0010.
- Rules and configuration reject unknown fields and labels, invalid or unbounded conditions, conflicting duplicate conditions, and tier references outside `router.auto`.
- The `x-spillway-route` header remains bounded to 256 bytes and contains only fixed labels, rule positions, configured tier names, and candidate positions.
  In rules mode it identifies the mode, matched rule position or `default`, difficulty, selected tier/candidate position within that tier's eligible candidates, and any fallback tier.
  Its form is `rules; rule <n>; difficulty <label>; tier <name>; candidate <n>/<m>` or the same form with `default` in place of `rule <n>`; fallback is marked with a fixed `fallback <tier>` segment.
  It never contains prompt text, classifier prose, or provider error text.
  The existing grammar for `direct`, explicit tiers, and legacy `auto` is unchanged (ADR 0008).
- Stage 2 classification uses only an explicitly configured local Ollama endpoint; it is disabled by default, bounded, and falls back to Stage 1 rules on failure.
- A stage is recommended for default enablement only when every promotion gate passes:
  - Mean estimated USD per request is at least 10% below current auto, where savings are `(current-auto mean - mode mean) / current-auto mean`, and the lower bound of the paired 95% bootstrap interval for savings is above 0%.
  - The upper bound of the paired 95% bootstrap interval for p95 end-to-end latency regression, calculated as `mode p95 / current-auto p95 - 1` within each prompt-level resample, is no more than 5%, including classifier overhead.
  - The lower bound of the paired 95% bootstrap interval for mean paired quality-score difference is above -0.2 points on a 5-point scale.
  - The upper bound of the paired 95% confidence interval for severe-correctness-failure rate difference is no more than +2 percentage points.
  - At least 95% of requests in each arm have a known cost estimate; report the reported, declared-price, estimated-token, and unknown shares separately.
- Pair and resample by prompt, keeping repeated trials together; report all metrics by difficulty as well as in aggregate.
  Define severe correctness failures before unblinding and adjudicate them separately from average rubric scores.
  If a gate fails or its confidence interval or cost coverage is inconclusive, the feature remains opt-in.

## Consequences

- Users can inspect and control every Stage 1 rule and fallback tier; no hidden heuristics alter their route.
- A moderate default avoids treating an unclassified request as simple.
- Explicit per-difficulty fallback lists avoid an implicit downgrade or upgrade when a selected tier is unavailable.
- The confidence and coverage gates make promotion evidence reproducible, but require enough paired prompts and known-cost traffic; inconclusive evidence means no promotion.
- New labels, implicit built-in rules, cross-difficulty fallback, relaxing the gates, changing existing route-reason grammar, or adding a remote classifier backend requires a new ADR.

## Evaluation outcome (2026-10-16)

The offline Stage 1 and Stage 2 harness runs did not pass the promotion gates.
Both used the zero-cost `mock/echo` provider, which makes cost savings undefined and cannot supply meaningful answer-quality or severe-failure ratings.
The Stage 2 run also had no local Ollama service, so all classifier requests fell back to deterministic rules.
The classifier therefore remains opt-in and disabled unless explicitly configured.
A model-backed paired run with known cost sources and independent blinded ratings is required before reconsidering default enablement; see [the Stage 2 evaluation report](../v0.5-ai-evaluation.md).

## Evaluation outcome (v1.0)

The owner ran a live 10-prompt-per-arm pilot and started the non-blocking 90-prompt comparison on 2026-10-16.
The full comparison stopped at prompt `s-015`, repeat 3, after OpenRouter rate limits and an upstream-unavailable response, followed by a request deadline on the rules endpoint.
The pilot cost $0.0034243, with reported cost for all pilot requests.
Five store-bearing attempts that day left 1,358 local request records with $0.120144 recorded cost and estimated token usage for 54 requests; these figures are not an authoritative provider bill.
Reconcile successful partial-run usage against the OpenRouter account before claiming the combined spend is under the $5 cap.
The first full attempt stopped at `s-015`, repeat 3, with a deadline error; later attempts stopped with HTTP 429 on the `google/gemma-4-31b-it:free` route, most recently at classifier prompt `s-010`, repeat 1.
The logs classify the 429 as `rate_limited`, but do not identify the specific limit; OpenRouter's documented free-model caps are 20 requests per minute and 50 per day.
No complete full-run report, blinded ratings, or gate verdicts were produced, so this run provides no basis to change routing defaults.
The classifier remains opt-in and disabled unless configured.
The run details, selected catalog prices and versions, and remaining limitations are recorded in [the v1.0 routing evaluation report](../v1.0-routing-evaluation.md).

A later run completed 810 trials using three paid low-cost OpenRouter candidates after earlier retries hit free-model rate limits.
Its 30-trial pilot and full run recorded $0.07323945 total, with reported costs for all 840 trials; this local figure still needs reconciliation against OpenRouter billing.
The candidate set does not include a zero-spend route.
The pre-rating `eval-report` shows classifier cost savings but fails the latency gate; rules do not meet the savings target.
Quality and severe-failure verdicts are inconclusive without independent ratings.
Provider billing reconciliation and independent ratings remain outstanding, so the routing defaults remain unchanged.
