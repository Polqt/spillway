# 33. Gemini thought signatures travel inside tool-call IDs

Date: 2026-10-28
Status: accepted

## Context

Gemini 3 and later models attach a thought signature to the first function call of each model step and reject the next request with 400 when the current turn's history omits it.
On Gemini's OpenAI-compatible endpoint (ADR 0001) the signature lives in `tool_calls[].extra_content.google.thought_signature`, a Google extension to the chat shape.
`/v1/chat/completions` passes it through verbatim, but the Responses and Anthropic Messages translators drop it, and Codex and Claude Code echo only the tool-call ID they must pair results with.
The resulting 400 does not spill (ADR 0006), so multi-step tool loops on Gemini fail outright.
Every candidate in a route receives the same request body, so anything provider-specific has to happen inside the provider adapter.
Spillway keeps no per-conversation state, and Responses `store` is ignored by design.

## Decision

- Inside Spillway the canonical home of a signature is Google's own field, `tool_calls[].extra_content.google.thought_signature`, on chat-shape assistant tool calls.
  The translators read it from chat responses and write it back when they rebuild chat history from a client request.
- On `/v1/responses` and `/v1/messages`, a tool call that has a signature reaches the client with a signed tool call ID instead of the provider ID:

  ```text
  spwts1_<base64url, no padding, of {"id":"<provider tool-call id>","ts":"<thought signature>"}>
  ```

  The alphabet `[A-Za-z0-9_-]` fits Anthropic's `tool_use.id` pattern and any string Responses `call_id`.
  Responses output signs only `call_id`; the item `id` stays the provider ID.
  An unsigned tool call keeps its provider ID unchanged, so output from other providers does not change.
- Inbound, the translators decode every position that pairs a call with its result: Responses `function_call.call_id` and `function_call_output.call_id`, Anthropic `tool_use.id` and `tool_result.tool_use_id`.
  An ID without the `spwts1_` prefix is a plain ID and passes through unchanged.
- One codec enforces the bounds.
  The provider tool-call ID is 1 to 256 bytes of printable ASCII without spaces.
  The signature is 1 to 64 KiB from the alphabet `[A-Za-z0-9+/=_-]`.
  A prefixed inbound ID is length-checked before decoding, then decoded with strict unpadded base64url and strict JSON with only `id` and `ts`, then validated against these bounds.
  Any failure is a 400 with the protocol's error shape, type `invalid_request_error` and code `invalid_request`, whose message names the input position and never echoes the ID or any decoded part.
  An outbound signature that is invalid or too large is not embedded; the client gets the plain provider ID, and Spillway logs one warning with `provider`, `reason` (`too_large` or `invalid`) and `bytes`, never the value.
- Providers shape tool-call history.
  The shared OpenAI-compatible client removes `extra_content` from every `messages[].tool_calls[]` entry unless its adapter opts in.
  It rewrites only the `messages` value, so every other top-level value stays byte-identical, and a body without `extra_content` is forwarded exactly as before.
  Only the Gemini adapter opts in, so only Gemini receives the field.
- When no call in an assistant tool-call message carries a signature, the Gemini adapter sets Google's documented placeholder `skip_thought_signature_validator` on the first call of that message.
  It never replaces a real signature and leaves the body byte-identical when nothing needs filling.
  Filling older turns is harmless because Google validates only the current turn, which spares Spillway from re-implementing Google's turn boundary rule.
  It applies to every Gemini model, because ADR 0007 rules out deriving what a model supports from its name.
  This covers calls generated by another provider before spillover, sessions recorded before this ADR, chat clients that drop `extra_content`, and signatures too large to embed.
- Translated streams on `/v1/responses` and `/v1/messages` accumulate tool-call deltas and emit each tool call's full event sequence only at `finish_reason` or `[DONE]`, in index order, with its final ID.
  Text deltas still stream live.
  Google may send the signature in a later chunk than the call's first, and Anthropic cannot change the ID of a block it has already started.

## Consequences

- The `spwts1_` format is part of the v1 stable surface (ADR 0015).
  Every v1 release keeps decoding `spwts1_` IDs, so resumed Codex and Claude Code sessions keep working across upgrades.
  A new envelope gets a new prefix, and the old prefix stays decodable for the rest of v1.
- ADR 0001's "requests pass through verbatim" narrows: the Gemini adapter may add the placeholder to unsigned assistant tool calls.
  Separately, Groq, OpenRouter and Ollama no longer receive `extra_content` on assistant tool calls.
  Every other part of a request body is still forwarded unchanged.
- Client transcripts hold longer tool-call IDs, and signatures are stored only there, in the client's own history.
- A signature is model-derived content: it never appears in logs, the usage store, `x-spillway-*` headers or error messages.
- A client-supplied signed ID is untrusted input; it is sent only to the Gemini instance chosen for the request, and a forged one only reaches the user's own key, where Gemini validates it.
- In translated streams, tool-call arguments arrive at the end of the stream, and an upstream failure mid-stream never delivers a partial tool call.
- Routing is unchanged: signatures never influence candidate order, spill conditions, cooldowns or route membership, and Gemini's own signature 400 still does not spill (ADR 0006).
- A real signature is forwarded even when the next candidate is a different Gemini model.
  On 2026-10-29 a `gemini-3.5-flash` signature was accepted on `gemini-3.5-flash-lite`, `gemini-3.1-flash-lite`, `gemini-3-flash-preview` and `gemini-3.6-flash`.
- Live `gemini-3.5-flash` signatures measured 360 and 436 bytes on 2026-10-29, far below the 64 KiB bound, giving signed IDs of about 550 characters that Codex and Claude Code replayed unchanged.
- The placeholder is accepted by `gemini-3.5-flash`.
  Whether Gemini 2.5 models accept it is unconfirmed: on 2026-10-29 Google answered 404 for `gemini-2.5-flash` and `gemini-2.5-flash-lite` on a free-tier key, although its model list still named them.

## Rejected alternatives

- Protocol-native reasoning carriers, a Responses `reasoning` item with `encrypted_content` or an Anthropic `thinking` or `redacted_thinking` block, need two mappings, depend on clients replaying reasoning that they may drop, tie a signature to a call only by position, and show empty thinking blocks in Claude Code.
- A server-side map from call ID to signature breaks statelessness, is lost on restart, needs bounded memory and eviction, and persisting model-derived content would contradict ADR 0009.
- The placeholder alone, as the primary path, is limited by Google to history it did not generate and degrades reasoning in exactly the multi-step loops this ADR fixes.
- An HMAC over the envelope adds a persistent local secret and key rotation for no security gain, because the authenticated local client already controls the whole prompt and Gemini validates signatures itself.
- Signed IDs on `/v1/chat/completions` would rewrite IDs on the OpenAI-contract path and surprise clients that already echo `extra_content`.
- Emitting a stream tool call on its first delta works only if Gemini always sends the signature in that delta, which Google does not promise.
