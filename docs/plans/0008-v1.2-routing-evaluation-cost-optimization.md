# v1.2 Routing Evaluation & Cost Optimization

Status: proposed; v1.1 is closed and local tickets are drafted for owner review. Implementation remains gated on ticket approval.

## Goal

Establish reproducible, privacy-safe evidence for comparing current `auto`, user-configured deterministic rules, and the optional local difficulty classifier.

Report answer quality, estimated cost, provider-reported request cost, latency, request success, and spillover reliability.

Use those results to identify weaknesses and propose routing improvements without changing routing defaults.

Keep paid evaluations opt-in, preserve the stable v1 surface, retain single-binary delivery, and add no dependency or hosted service.

## Current evidence

The evaluation runner already randomizes arm order and records seed, corpus hash, model usage, latency, and cost source.

It currently writes completion text and assignment data, returns on the first failed trial, and writes run artifacts only after all trials complete.

The current trial record does not retain explicit request outcome, response status, route reason, or spillover success.

The v1.0 report records 810 full-run trials and reports 11.9053% classifier cost savings with a 47.8794% p95 latency regression.

Rules routing reports -0.0557% cost savings in that run.

Independent ratings and provider billing reconciliation remain outstanding, so those results do not support routing-default changes.

## Scope

- Make runs resumable and preserve safe partial reports with an explicit outcome for every attempted trial.
- Separate provider-reported request cost from configured-price estimates, token estimates, free requests, and unknown costs.
- Record the metadata needed to reproduce a run without storing prompts, responses, or credentials in Spillway outputs.
- Benchmark deterministic rules and the available optional Ollama classifier against current `auto` using paired prompts and identical candidate sets.
- Report request success, first-token and total latency, spillover selections, successful spillovers, exhaustion, rate limits, timeouts, and incomplete streams.
- Import independently completed human ratings by opaque trial ID and report agreement and paired quality gates.
- Add CLI aggregate reporting first, then consider a small dashboard view backed only by opt-in aggregate metadata.
- Publish evidence-backed routing recommendations while leaving runtime routing unchanged.

## Privacy and cost boundaries

The operator supplies and retains a versioned evaluation corpus outside Spillway.

Spillway records a corpus digest, version, count, categories, settings fingerprint, and environment metadata.

Prompt and response content remains in memory during requests and in an operator-managed temporary blinded review export.

The export is written only to an operator-selected temporary directory, keeps the blind-key mapping separate from both rater views, and includes a deletion checklist; it is never included in durable evaluation reports.

Persisted evaluation output may contain run metadata, opaque trial IDs, ratings, assignments after blinding ends, and aggregate metrics.

Provider keys remain in environment variables or the operator's secret manager and never enter reports, logs, store rows, or dashboard responses.

The default evaluation configuration uses the mock provider and makes no paid requests.

Every live paid run requires explicit operator approval and a declared estimated-cost ceiling.

No new paid benchmark may start until T19 is resolved or the owner approves a documented recovery path that addresses the missing T19 evidence.

Provider-reported request cost is not treated as provider account billing.

Billing reconciliation uses a dedicated provider usage window and retains only aggregate totals, the variance, and an explanation.

## Measurement protocol

Use an operator-held corpus with at least 90 prompts, 30 prompts per difficulty, and declared task categories.

For a three-arm comparison, run three repeats per prompt and arm, randomize arm order with a recorded seed, disable caching, and hold the candidate set and generation settings constant.

Preselect one repeat per prompt and arm using a recorded schedule, then have both independent raters score that same answer; with 90 prompts and three arms, this yields 90 rated answers per arm and 270 total, each with two independent ratings.

Raters use the existing correctness, completeness, instruction-following, and severe-correctness-failure rubric.

Adjudicate severe-failure disagreements while ratings remain blinded.

Pair and resample by prompt, keep repeats together, use a recorded bootstrap seed, and run at least 10,000 replicates.

Report aggregate results and results by difficulty and category.

Preserve all ADR 0014 promotion gates.

Add a reliability gate requiring the lower paired 95% confidence bound for request-success difference versus current `auto` to be at least -2 percentage points.

Report spillover selection and successful spillover separately, and classify an incomplete stream as an unsuccessful request.

Do not promote a route when any gate fails or remains inconclusive.

### V12-00: Close T19 ratings and billing reconciliation

**Blocked by:** Recovery of the original matching full-run packet and provider billing evidence.

**Acceptance:** Two independent raters complete every required blinded score; severe-failure disagreements are adjudicated before unblinding; the final report includes agreement and all ADR 0014 gates; provider account totals are reconciled against the dedicated run window and any variance is documented.

**Safety:** Do not score the v1.0 pilot or unrelated v0.5 packets as substitutes for the missing full-run packet.

If the matching packet is unavailable, leave this ticket blocked and attach a recovery or rerun proposal.

Do not run a paid rerun until the owner separately approves it.

### V12-01: Approve the evaluation privacy and measurement contract

**Blocked by:** v1.1 closure.

**Acceptance:** ADR 0022 and ADR 0023 agree on metadata fields, cost-source labels, failure outcomes, content-retention boundaries, and promotion gates.

The contract preserves ADR 0014's gates and adds the request-success reliability gate.

No decision changes default routing or stable API/config behavior.

### V12-02: Make evaluation trials resumable and preserve partial runs

**Blocked by:** V12-01.

**Acceptance:** Every attempted trial has a stable opaque ID, arm, prompt cluster ID, repeat, start/end timing, outcome enum, HTTP status class when available, and safe route metadata.

The runner writes metadata atomically after each trial and resumes completed trial IDs without resending them.

Failed trials are not retried automatically; an explicit retry option identifies the exact failed IDs and warns that duplicate provider charges may occur.

Interrupted streams and cancelled requests produce explicit partial outcomes.

Tests verify that prompts, responses, provider keys, local keys, and provider error bodies do not enter any output artifact.

An explicit operator-invoked review export may write blinded prompt/response material only to an operator-selected temporary directory; it must be clearly separated from durable reports and include a deletion checklist.

### V12-03: Separate cost sources and add spillover reliability metrics

**Blocked by:** V12-02.

**Acceptance:** Each report separately summarizes provider-reported request cost, declared-price cost, token-estimated cost, zero-cost requests, unknown cost, and coverage.

Reports include request success, status-class counts, total and first-token latency, fallback candidate selection, successful spillover, exhaustion, and incomplete-stream rate.

Provider billing is labeled external reconciliation data and never conflated with request-reported cost.

The stable `/v1/*` contract and route grammar remain unchanged.

### V12-04: Import independent ratings and calculate promotion gates

**Blocked by:** V12-03.

**Acceptance:** Two independently identified score sheets are validated against opaque trial IDs and the assignment map.

The review export produces independently shuffled rater views and keeps the blind-key mapping outside both rater materials.

The reporter rejects duplicate, missing, conflicting, or unadjudicated severe-failure ratings.

It reports inter-rater agreement, paired bootstrap intervals, each existing ADR 0014 gate, and the new request-success gate.

No response packet or prompt text is required by the report command.

### V12-05: Benchmark deterministic rules against current `auto`

**Blocked by:** V12-00 and V12-04. No paid requests until T19 is resolved or the owner approves its documented recovery path, and the specific benchmark run, candidate set, and cost ceiling are approved.

**Acceptance:** The benchmark uses the same candidate set and generation settings across arms, a fixed corpus digest and seed, disabled caching, and a completed pilot before the full run.

It reports every metric overall and by difficulty/category.

The analysis identifies where existing size/tool rules appear to over-route or under-route, with supporting rated examples handled only in the temporary blinded review process.

It proposes config-level rule changes only; runtime defaults remain unchanged.

### V12-06: Evaluate the optional local classifier

**Blocked by:** V12-05 and an explicitly configured, digest-pinned Ollama model.

**Acceptance:** The classifier is evaluated with the same candidates and corpus as current `auto` and rules.

The report includes classifier overhead, p50/p95 latency, label distribution, fallback rate, request success, cost, quality, and severe-failure results.

Unavailable Ollama, timeout, invalid-label, and uncertain-output cases are measured as deterministic fallback behavior.

The classifier remains opt-in and disabled by default.

### V12-07: Add CLI aggregate evaluation reports

**Blocked by:** V12-04.

**Acceptance:** Experimental CLI output summarizes run identity, candidate arms, cost-source shares, latency, success/spillover metrics, human-rating agreement, confidence intervals, and gate verdicts.

Output contains no prompt, response, or credential data.

Existing experimental command compatibility is maintained where practical; any format change is documented because evaluation commands are outside the stable CLI surface.

### V12-08: Add an opt-in dashboard evaluation summary

**Blocked by:** V12-07 and the core benchmark report schema.

**Acceptance:** With `store:` enabled, the dashboard can show a bounded list of aggregate evaluation runs.

The endpoint requires a dashboard key, uses `Cache-Control: no-store`, and returns only metadata, ratings, and aggregate metrics.

Without `store:`, no evaluation result file or database is created by the dashboard path.

The UI uses the existing embedded Preact/Vite build and adds no runtime or build dependency.

### V12-09: Publish the evidence and close v1.2

**Blocked by:** V12-00 through V12-08, except V12-08 may be explicitly deferred by the owner.

**Acceptance:** The report records reproducibility metadata, all gate results, billing reconciliation status, privacy checks, and limitations.

Every recommendation is labeled as supported, rejected, or inconclusive with measured evidence.

No routing default changes without separate explicit approval.

## Proposed ADRs

- ADR 0022: Privacy-safe evaluation artifacts and temporary blinded review.
- ADR 0023: Request-success and spillover reliability gate for routing evaluation.

Both ADRs remain proposed until approved.

## Non-goals

- Changing routing defaults or automatically editing user rules.
- Adding an LLM judge, semantic cache, provider, framework, dependency, cloud service, or telemetry.
- Persisting prompts, responses, or provider credentials in Spillway.
- Replacing the evaluation package, CLI, SQLite store, or embedded dashboard stack.
- Running paid evaluations or publishing a release before owner approval.

## Definition of done

- v1.1 is closed with all eight tickets' acceptance criteria verified and T19 remains separate from that release gate.
- T19 is rated and reconciled from matching evidence, or its missing-packet limitation and owner-approved recovery plan are recorded without claiming completion.
- Resumable partial evaluation runs, explicit outcomes, cost-source separation, and reliability metrics pass their acceptance tests.
- The benchmark report is reproducible from the same operator-held corpus and metadata, without persisted content or credentials.
- The approved human-rating and statistical gates are reported overall and by difficulty/category.
- Any dashboard view is opt-in, dashboard-key protected, content-free, bounded, and covered by API and browser tests.
- `make check`, `make build`, and `CGO_ENABLED=0 go build ./...` pass.
- Routing defaults, stable API behavior, single-binary delivery, and zero-spend defaults remain intact.
