# v0.3 Rules Router: `model: "auto"`

Status: complete; shipped in v1.0.0; approved (2026-10-15; every decision accepted with its recommended option; ADR 0007 and ADR 0008 accepted)
Milestone: v0.3

## Goal

A client app sends `model: "auto"` and Spillway picks the model itself, deterministically, from the user's tiers.
It detects what the request needs from the request body (tools, vision, JSON mode, structured outputs, and a conservative size estimate) and routes only to candidates whose capabilities the user declared, free tiers first.
Every routed response explains itself in an `x-spillway-route` header, and a request no candidate can support gets one clear 400 instead of a confusing provider error.
v0.2 spillover, cooldowns and circuit breakers are reused unchanged.

## Capability sources (what is reliable)

| Source | What it gives | Used in v0.3 |
|---|---|---|
| The request body | Exactly what this request needs: `tools`/`functions`, tool messages, `image_url` parts, `response_format.type` | Yes: requirements |
| User config (`models:`) | What the user states a model supports | Yes: the only capability source |
| OpenRouter `GET /models` | `supported_parameters` (tools, response_format, structured_outputs), `architecture.input_modalities`, `context_length` | Deferred to v0.4 with catalog and pricing |
| Ollama `POST /api/show` | `capabilities` (tools, vision), context length | Deferred to v0.4 |
| Groq `GET /models` | `context_window` only | Deferred to v0.4 |
| Gemini OpenAI-compatible `GET /models` | No capability fields | Never |
| Model names ("vision", "70b") | Guesswork | Never |

Consequence: in v0.3 a capability is true only because the user declared it.
Catalog discovery is a separate source with its own failure modes (startup network calls, staleness, partial coverage) and belongs with the v0.4 catalog work that already fetches pricing.
The field shapes in the deferred rows come from provider documentation and must be re-checked when that work is planned.

## Scope

In (MVP):
- `models:` config: per model reference, a complete `capabilities` list from a closed set (`tools`, `vision`, `json_mode`, `structured_outputs`) and an optional `context_window`.
- `router.auto`: an ordered list of tier names; `auto` resolves to their candidates in order, de-duplicated; zero-spend tiers must come before any `allow_spend` tier.
- Requirement detection from the request body, for `auto` and `spillway/<tier>` only.
- Capability filtering before any attempt, with the three-state rule in Decision 2.
- A context filter that skips a candidate only when its declared window is clearly too small.
- New `internal/router` package: tier and auto resolution, detection, filtering and the route reason, as pure functions of config and request body.
- `x-spillway-route` header on every chat response, direct included; the access log gains `route`.
- 400 `no_capable_model` (or `context_length_exceeded`) when filtering leaves no candidate; v0.2 exhaustion (429 or 503) when eligible candidates exist but all fail.
- `/v1/models` lists `auto` when `router.auto` is configured.
- ADR 0007 and ADR 0008, GLOSSARY and CONTEXT updates, example configs.

Deferred:
- Capability discovery from OpenRouter, Ollama and Groq catalogs: v0.4, with pricing.
- User-written rules (`when: {client_app: x} -> tier`), prompt-length tiers, difficulty: v0.5 with the classifier, or when a real case needs them.
- Spilling on a provider's `context_length_exceeded` 400: needs an ADR 0006 change, since 400 does not spill today.
- Detecting audio input, file parts, `modalities`, `n > 1`, `logprobs`: such requests pass through as in v0.2 and may get a provider 400.
- Capability filtering for direct model references: never planned; an explicit model reference is the client's choice (ADR 0006).
- The `router.mode`, `judge_model` and `confidence_threshold` keys from CONTEXT section 7: v0.5; rejected until then.

## Design

### Config

```yaml
tiers:
  free:
    models: [groq/llama-3.3-70b-versatile, gemini/gemini-2.5-flash, ollama/llama3.2:3b]
  smart:
    allow_spend: true
    models: [openrouter/anthropic/claude-sonnet-4.5]

models:                                   # capability declarations; the only capability source in v0.3
  groq/llama-3.3-70b-versatile: { capabilities: [tools, json_mode], context_window: 131072 }
  gemini/gemini-2.5-flash:      { capabilities: [tools, vision, json_mode, structured_outputs], context_window: 1048576 }
  ollama/llama3.2:3b:           { capabilities: [] }  # declared: text only

router:
  auto: [free, smart]                     # free first; smart may spend because it says allow_spend
```

Validation (each error names the YAML path and the fix):
- `models` keys parse with `providers.ParseModelRef` and must appear in at least one tier, which catches typos because declarations only affect tier and auto routing.
- `capabilities` is required in every entry (an empty list means text only), holds only the four names, and has no duplicates.
- `context_window`, when present, is an integer from 1 to 10,000,000.
- `router` accepts only `auto`; other keys fail with "not supported until v0.5".
- `router.auto` names 1 or more configured tiers, no duplicates; a zero-spend tier after an `allow_spend` tier fails with `router.auto[0]: tier smart allows spend and must come after every zero-spend tier (ADR 0008)`.
- The de-duplicated auto chain holds at most 16 candidates, the same per-request attempt bound as one tier.
- Tier model references must be printable ASCII without spaces, because they now reach a response header; existing valid references already are.

### Requirements

Detected from `RawBody` for virtual models only, with one small typed decode:

| Requirement | Detected when |
|---|---|
| `tools` | `tools` or `functions` is a non-empty array, or any message has role `tool` or `function`, or a non-null `tool_calls` or `function_call` |
| `vision` | any message content part has `type: "image_url"` |
| `json_mode` | `response_format.type` is `json_object` |
| `structured_outputs` | `response_format.type` is `json_schema` |
| size | `ceil(text bytes / 6)` over message text parts and tool definitions, plus `max_completion_tokens` (or `max_tokens`) when set |

A field of the wrong JSON type (`tools: "x"`) is a 400 `invalid_request_error` naming the field, for virtual models only; direct references keep forwarding the body untouched.
The size estimate divides by 6 so it undercounts for ordinary text (about 4 to 5 bytes per token in English, fewer in code and CJK), which means a candidate is skipped only when the request is clearly larger than its window; images are not counted.

### Filtering (Decision 2)

For each candidate in order, with the request's requirement set R:
- R empty: eligible, whatever is declared.
- Declared: eligible if it declares every capability in R; otherwise skipped, reason `lacks vision`.
- Not declared, in a `spillway/<tier>` request: eligible, as in v0.2, because the user picked that tier explicitly.
- Not declared, in an `auto` request with R not empty: skipped, reason `capabilities not declared`, because Spillway is choosing and must not guess.
  An `auto` request with R empty reaches undeclared models like any other (first rule).
- Declared `context_window` smaller than the size estimate: skipped, reason `context too small (est. 41000 > 32768)`, in both cases.

Filtering never reorders: eligible candidates keep tier order, so routing stays deterministic.

### internal/router

One small interface, pure and offline, no clock, no I/O:

```go
type Capability string // "tools", "vision", "json_mode", "structured_outputs"

type Declaration struct {
    Capabilities  []Capability
    ContextWindow int // 0 when undeclared
}

type Options struct {
    Tiers        map[string][]providers.ModelRef
    Auto         []string                                // tier names, validated by config
    Declarations map[providers.ModelRef]Declaration
}

func New(o Options) (*Router, error)

// Plan resolves a virtual model for one request body. ok is false for a
// model that is not virtual, which the caller treats as a direct reference.
func (r *Router) Plan(model string, body []byte) (plan Plan, ok bool, err error)

type Plan struct {
    Source     string               // "auto" or "tier"
    Tiers      []string             // the tier of each eligible candidate
    Needs      []Capability         // sorted
    Eligible   []providers.ModelRef // tier order
    Skipped    []Skip               // ref and reason, for the log and error messages
}
```

`Plan` errors are typed: `ErrUnknownTier` (404, lists tiers), `ErrAutoNotConfigured` (404, says to set `router.auto`), `ErrInvalidField` (400), `ErrNoCapableModel` (400, lists skips; carries whether every skip was context).
The spillover loop, the tracker and HTTP stay in `internal/api`; the tier lookup moves from `api.chatHandler.ServeHTTP` into `Plan`.

### internal/api changes

- `api.Options` gains `Router planner` (consumer-side interface with `Plan`); `Tiers` moves into the router; `/v1/models` lists tier names and `auto` from the router.
- `ServeHTTP`: `Plan` first; not virtual keeps the v0.1 direct path; a plan error maps to its status; otherwise `serveTier` runs over `plan.Eligible` exactly as today, with `plan.Skipped` pre-seeded into the failure list for the exhaustion message.
- `earliestCooldown` counts only eligible candidates, so a tier where the capable candidates are all cooling still answers 429 with `Retry-After`.
- `ErrNoCapableModel`: 400, `type: invalid_request_error`, code `context_length_exceeded` when every skip was size (OpenAI's own code), else `no_capable_model`.
  Message: `No model for "auto" supports this request, which needs tools, vision: groq/llama-3.3-70b-versatile lacks vision; ollama/llama3.2:3b lacks tools, vision. Declare capabilities under models: (ADR 0007).`
- Streams: plan errors are plain JSON, never SSE, because they happen before any attempt.

### x-spillway-route (Decision 4)

```
direct
tier free; candidate 2/3
tier free; needs tools; candidate 1/2
auto; needs tools, vision; tier smart; candidate 3/3
auto; needs vision; no capable model
auto; needs tools; exhausted (2 eligible)
```

- `candidate n/m`: position among the eligible candidates; `m` excludes capability skips, so the header says how far down the list the request went.
- Built only from fixed words, validated tier names and capability names; never prompt text, keys or provider error text; at most 256 bytes.
- Set per candidate before the provider call and cleared with the other candidate headers, so streams carry the value of the candidate that committed; also set on plan errors and exhaustion.
- The access log gains `route` with the same value.

### Hard-rule check

- No quota evasion: auto only draws from tiers; one key per provider; spillover rules unchanged.
- No credential collection, secrets never leak: no new secret; the header and messages use config names only; tests assert keys absent from header, body and log.
- Single binary, no cgo: no new dependency.
- Local by default: no new outbound call; detection and filtering are offline.
- OpenAI compatibility: request bodies forwarded verbatim; `context_length_exceeded` is OpenAI's code; new error codes use the OpenAI error shape; SDKs ignore unknown headers.

## Acceptance criteria and offline test scenarios

All offline: the mock provider, in-test fake providers, `httptest.Server` fixtures; time via `testing/synctest` where cooldowns are involved.

- **Auto picks the first capable free candidate.** `router.auto: [free, smart]`, a tools request, `free` = `[a (undeclared), b (declared [json_mode]), c (declared [tools])]`: `c` serves; header `auto; needs tools; tier free; candidate 1/1`; `a` and `b` record zero calls.
- **Free first.** Same request when `c` is cooling: the `smart` candidate serves; header names `tier smart`; config with `[smart, free]` is refused with the ADR 0008 message.
- **No capable model.** A vision request where nothing declares `vision`: 400 `no_capable_model`; message lists every candidate and reason, contains no key, is under 2 KiB; zero provider calls; streaming gives the same JSON body, no SSE.
- **Context.** Declared window 32768 and a 300 KB text prompt: skipped with the `context too small` reason; every candidate skipped for size gives 400 `context_length_exceeded`; a 100 KB prompt is not skipped; a 2 MB base64 image does not count.
- **Tier compatibility.** Every v0.2 tier test passes unchanged except added header assertions; a tools request to a tier with no declarations is tried exactly as in v0.2.
- **Tier filtering.** A tools request to `spillway/free` where `b` declares `[json_mode]`: `b` is skipped, reason `lacks tools`.
- **Exhaustion over eligible only.** Capable candidates all cooling with known times, others skipped for capability: 429 with `Retry-After` = earliest; header ends `exhausted (n eligible)`.
- **Spillover reused.** In `auto`, a capable candidate returning 429 spills to the next capable one; breaker and cooldown behaviour identical to v0.2 (shared tracker).
- **Determinism.** Same config, body and failure history: same eligible list and same header, 100 runs.
- **Header safety.** The header never contains message text, keys or upstream error text across the scenario table; at most 256 bytes; reset between attempts so a streamed response names the committing candidate.
- **Detection table.** Each row of the requirements table, plus negatives: `tools: []`, `response_format: {type: text}`, a string `content`, unknown content part types; wrong-type `tools` is a 400 for `auto` and forwarded untouched for a direct reference.
- **Unchanged.** Direct model references: no detection, no filter, header `direct`, body forwarded byte for byte; a config without `models:` and `router:` behaves exactly as v0.2.
- **Concurrency.** 50 parallel mixed `auto` and tier requests under `-race`, no race, every request answered.

## Risks

1. **Declaration burden and staleness.** Users must declare capabilities by hand, and a provider can change a model. A wrong "yes" gives a provider 400 that does not spill; a wrong "no" skips a model that would have worked. Mitigation: clear skip reasons in the header, log and error; catalog discovery in v0.4.
2. **Different strictness for tiers and auto.** An undeclared model is tried by `spillway/<tier>` and skipped by `auto`. Chosen to keep v0.2 behaviour while keeping auto honest; stated in ADR 0007 and the skip reason.
3. **Size heuristic.** No tokenizer, so the estimate can miss a request that is slightly too large (provider 400, as in v0.2); it is biased to miss rather than wrongly skip.
4. **Undetected needs.** Audio, files and other features pass through undetected and can 400 on a candidate that lacks them.
5. **Auto can spend.** Only when the user lists an `allow_spend` tier in `router.auto`, and only after every zero-spend candidate is skipped or failed; the header names the tier that served.
6. **Header exposure.** The header reveals tier names and capability names to the authenticated client app; the same app already sees `x-spillway-model`.

## Self-review

Gaps found and closed:
- A capability-filtered candidate has no resume time, so v0.2's `earliestCooldown` would turn a "capable ones are cooling" case into 503; it now counts eligible candidates only.
- Without a required `capabilities` list, an entry with only `context_window` would silently mean "text only"; the list is required, so declared always means complete.
- Unbounded auto chains would break ADR 0006's attempt bound; capped at 16.
- Model references now reach a header; printable-ASCII validation keeps header values clean.

Cut as overengineering:
- Catalog discovery, a rule DSL, per-client-app routing, prompt-length tiers, reordering by capability fit, scoring, a separate `capabilities` package, spilling on context 400s.
- What remains new: one package (`router`, one type, one method), two config sections, one header.

## Decisions

Resolved 2026-10-15: every decision below was accepted with its recommended option.

1. **Capabilities come only from explicit `models:` declarations in v0.3; catalog discovery waits for v0.4.** Alternative: fetch OpenRouter and Ollama catalogs at startup. Recommended: config only, because it adds no outbound calls, no startup failure modes and no staleness, and nothing is claimed without the user saying so. ADR 0007.
2. **Three-state filtering: undeclared models are tried by tiers (v0.2 compatibility) and skipped by `auto` only when the request has at least one capability requirement; a plain `auto` request may reach them.** Alternatives: strict everywhere (breaks v0.2 tier behaviour), or lenient everywhere (auto would guess). Recommended as stated. ADR 0007.
3. **`auto` is an ordered chain of tiers (`router.auto`), zero-spend tiers first, enforced by config; spending only through a listed `allow_spend` tier.** Alternatives: a rule DSL mapping request features to tiers, or all zero-spend models implicitly. Recommended: the chain, because capability filtering already does the per-request selection. ADR 0008.
4. **`x-spillway-route` uses the fixed grammar above and appears on every chat response, direct included.** Alternative: key=value pairs, or tier and auto responses only. Recommended: readable phrases in the style of CONTEXT section 6, on every response so clients can always rely on it. ADR 0008.
5. **Context filtering uses `ceil(bytes / 6)` plus requested output tokens against a declared `context_window`, skipping only clear overflows.** Alternative: defer context filtering until a tokenizer or provider count exists. Recommended: include, since false skips are rare by construction and misses fall back to v0.2 behaviour.
6. **Plan errors: 400 `no_capable_model`, or `context_length_exceeded` when only size disqualified; 404 for unknown tier or unconfigured auto.** Recommended; a 400 is not retried by SDKs, which is right because retrying cannot help.
7. **A new `internal/router` package holds resolution, detection, filtering and reasons; the spillover loop stays in `internal/api`.** Alternative: grow `api/chat.go`. Recommended: the package, which `AGENTS.md` already reserves for v0.3 and which keeps routing testable without HTTP.
