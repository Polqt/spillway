# v0.5 Smart Routing

Status: complete
Milestone: v0.5

## Goal

Route virtual auto requests to the lowest-cost tier that is likely to meet the request's difficulty, while preserving declared capability checks, budgets, spillover, and an understandable route reason.
Deliver this in two stages: deterministic difficulty rules first, then an optional AI classifier.
Use a paired evaluation to determine whether either stage reduces estimated cost without a material latency regression or answer-quality loss.

## Starting point

- v0.3 routing is deterministic and uses requirements, configured declarations, tier order, quota state, and budgets.
- ADR 0008 makes the x-spillway-route reason a public contract.
- v0.4 records per-request and per-attempt usage, cost estimates, latency, and route reasons.
- v0.4 validation is recorded in .scratch/v0.4-observability/validation-2026-10-15.md.
- The existing auto chain remains the baseline and remains available as a mode.

## Compatibility and safety constraints

- Explicit provider model references and spillway/<tier> requests retain their current behavior.
- Existing configurations without the new routing settings retain the current auto behavior.
- Difficulty selection may narrow or order configured tiers, but cannot bypass capability declarations, quota checks, budget checks, or provider spillover rules.
- A classifier never chooses a provider model directly; it returns a closed difficulty label that maps through user-configured tiers.
- Routing reasons contain only bounded fixed labels, configured tier names, and fixed skip reasons; never include prompt text or model-generated prose.
- AI classification is disabled unless explicitly configured and makes calls only to the user's configured local Ollama endpoint.
- Classifier input and output are never persisted; v0.4 usage records continue to contain metadata only.
- No multi-account rotation, cross-app cache sharing, remote telemetry, or unconfigured outbound calls.

## Stage 1: deterministic difficulty rules

Add an opt-in deterministic mode for auto routing.
Use bounded request features available locally, such as estimated input and requested output tokens, tool count, declared requirements, and simple structural signals.
Do not infer model capabilities from names or use external catalog data.

Recommended config shape:

    router:
      mode: rules
      auto: [cheap, balanced, strong]
      difficulty:
        simple: [cheap]
        moderate: [balanced]
        hard: [strong]
      rules:
        - when:
            estimated_input_tokens_gte: 12000
          difficulty: hard
        - when:
            tools_present: true
          difficulty: moderate

This is an opt-in, user-defined ruleset; v0.5 adds no implicit built-in matching rules.
Rules are evaluated in listed order and the first match wins; route reasons identify a match by its 1-based position.
The default difficulty is `moderate`, so a request with no matching rule does not silently take the least capable route.
`router.difficulty` maps each closed label (`simple`, `moderate`, `hard`) to a non-empty, ordered list of tiers already listed in `router.auto`.
These tier lists are the complete fallback order for that difficulty: tiers and their candidates are tried in order, keeping only the first occurrence of a model across the full list so each candidate is attempted at most once per request.
Exhaustion returns the existing no-candidate error rather than silently crossing into another difficulty.
Configuration validation rejects unknown fields or labels, invalid/unbounded conditions, duplicate conditions with conflicting outcomes, and tiers absent from `router.auto`.
The configured order must preserve zero-spend tiers before tiers that allow spending; existing quota, budget, capability, context-window, and spillover checks still apply to every candidate.
The deterministic default and each match emit a bounded route reason naming the mode, matched rule position or `default`, difficulty, tier, and candidate position among that tier's eligible candidates; fallback is identified with a fixed label and tier name.

Stage 1 includes the shared offline evaluation harness and baseline measurements so its result can be compared with today's auto behavior.

## Stage 2: optional AI classification

Add an opt-in classifier mode that sends a bounded classification request only to a configured local Ollama model.
Require a pinned model reference, a strict timeout and input/output size bounds.
Validate the response against a closed schema containing only a difficulty label and, if needed, a fixed reason code.
Reject free-form output, unknown labels, malformed data, and unsupported model results.

On timeout, connection failure, invalid output, or an uncertain result, fall back to Stage 1 deterministic rules and record a fixed fallback reason.
Do not add a hosted classifier or make provider API calls for classification in this milestone.
Keep this stage optional and retain deterministic mode as the default and fallback.

## Evaluation protocol

Compare three arms on the same versioned, representative prompt set: current auto routing, Stage 1 deterministic rules, and Stage 2 AI classification when enabled.
Use identical candidate models, prompts, generation settings, prices, and repeated trials where the provider supports reproducible settings.
Randomize arm order and pair each prompt across arms.
Keep evaluation prompts and completions out of the production usage store and normal logs.
Use fake providers and fixed outputs for automated tests; any live-provider quality run is an explicit manual evaluation and never part of CI.

Measure:

- Estimated USD per request and per evaluation set, using v0.4 cost-source precedence and recording the fraction of reported, declared, estimated, and unknown costs.
- End-to-end latency and time to first token, with p50 and p95; include classifier overhead.
- Answer quality from blinded paired ratings on a 1-to-5 rubric for correctness, completeness, and instruction following.
- Safety or correctness failures separately, so an average score cannot hide a severe regression.

Promotion gates, confirmed for v0.5:

- Mean estimated USD per request is at least 10% lower than current auto, where savings are `(current-auto mean - mode mean) / current-auto mean`, and the lower bound of the paired 95% bootstrap confidence interval for savings is above 0%.
- The upper bound of the paired 95% bootstrap confidence interval for p95 end-to-end latency regression, calculated as `mode p95 / current-auto p95 - 1` within each prompt-level resample, is no more than 5%; classifier overhead is included.
- The lower bound of the paired 95% bootstrap confidence interval for mean quality-score difference is above -0.2 points on the 5-point scale.
- The upper bound of the paired 95% confidence interval for the severe-correctness-failure rate difference is no more than +2 percentage points. Severe failures are adjudicated before unblinding and reported separately from the average quality rubric.
- At least 95% of requests in each arm must have a known estimated cost, with reported, declared-price, estimated-token, and unknown shares reported separately. If this coverage gate or a confidence bound cannot be estimated usefully, the cost result is inconclusive and the stage is not promoted.
- Report all measures by difficulty label as well as in aggregate; pair and resample at the prompt level so repeated trials for one prompt stay together.

If any gate is not met, or its required confidence interval cannot be estimated, keep the feature opt-in, document the result, and revise the rules or classification model before recommending it.

## Acceptance criteria

- Existing configurations, direct model references, and explicit tiers retain their current routing behavior.
- Stage 1 rule evaluation is deterministic, bounded, config-validated, unit tested, and explains every decision without including prompt content.
- Capability, quota, budget, spillover, and cost accounting remain enforced after difficulty selection.
- Stage 1's offline tests verify cost-aware tier choice and fallback when the preferred tier is unavailable or over budget.
- Stage 2 is disabled by default, uses only the explicitly configured local classifier, validates structured output, and falls back deterministically on all classifier errors.
- Tests verify classifier timeout, malformed output, unknown label, missing classifier configuration, and request cancellation without external services.
- Both stages are compared to current auto using the shared evaluation protocol and proposed promotion gates.
- Record outcomes and any threshold changes in the plan before recommending default enablement.
- Add ADRs for difficulty semantics, configuration precedence, public route-reason changes, classifier failure behavior, and local model calls.
- Update CONTEXT, GLOSSARY, examples, and user-facing documentation.
- make check and CGO_ENABLED=0 go build ./... pass before milestone completion.

## Out of scope

- Semantic caching, prompt or completion persistence, and automatic multi-turn quality escalation.
- Training, downloading, or bundling classifier weights in the Spillway binary.
- Remote classifier APIs, telemetry, or automatic rewriting of provider/model configuration.
- Changing the contract for explicit model or tier requests.

## Delivery sequence

1. Resolve the rule schema, fallback semantics, and evaluation thresholds.
2. Build the evaluation corpus format and baseline runner.
3. Implement and evaluate Stage 1 deterministic rules.
4. Implement Stage 2 local AI classification behind explicit opt-in and evaluate it against both baselines.
5. Review results, update docs and ADRs, then decide whether either mode is recommended for users.

## Resolved decisions

Stage 1 policy, evaluation gates, route-reason compatibility, and the local Ollama-only classifier backend are resolved in ADR 0014.

## Milestone outcome

Both routing stages are implemented and remain opt-in.
Offline paired runs verified the evaluation harness and deterministic fallback, but did not establish that either stage meets the promotion gates.
See [Stage 1 results](../v0.5-stage1-evaluation.md) and [Stage 2 results](../v0.5-ai-evaluation.md).
