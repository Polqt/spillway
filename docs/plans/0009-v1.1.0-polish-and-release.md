# v1.1.0 Final Polish and Release

Status: approved for ticketing 2026-10-19; tickets published under `.scratch/v1.1.0-release/issues/`
Milestone: v1.1.0

## Goal

A first-time developer can configure supported providers once, point any OpenAI-compatible client app at one local endpoint with one local key, and see spillover to the next eligible candidate when an earlier candidate is in cooldown, rate limited or failing.
v1.1.0 ships that experience from a verified single binary whose reported version is correct on every install channel.
The release line excludes v1.2 routing-evaluation work, and T19 stays independent and non-blocking.

This is a planning document.
It authorizes no implementation, branch operation, tag, push or publication.

### CLI observations from the `77e266b` binary

- Root help has a useful quick start, but the commands are one flat list in which the experimental `eval*` commands sit beside `init`, and Cobra's default `completion` and `help` descriptions are capitalized unlike the rest.
- Help lists flags as `--config`, while every doc and example uses `-config`; both forms work, but nothing says so.
- A misspelled command (`spillway serv`) prints the right suggestion followed by the entire root usage, which buries the suggestion.
- Missing environment variables are named precisely (`providers.groq.api_key (line 8): environment variable GROQ_API_KEY is not set`), but the hint does not show how to set one in the current shell.
- A listen conflict names the address and says to choose another, but gives no example line and does not mention that the client base URL must change too or that an older Spillway may still be running.
  On this machine port 8080 was held by an unrelated container that answered with HTTP 401, which a first-time user could mistake for a Spillway key problem.
- `init` success says the local key "is stored in that file" but not which entry a client app should use (`default`) versus the dashboard (`dashboard`), and does not suggest the `auto` model.

### Version and installed-binary observations

- `~/go/bin/spillway.exe` on this machine is v1.0.0 from `go install` and is first on `PATH`; installing a v1.1.0 archive elsewhere would leave the old binary in use unless the user checks.
- Release archives report `spillway 1.0.0` (GoReleaser `{{ .Version }}` drops the `v`), while `go install ...@v1.0.0` reports `spillway v1.0.0`.
- `make build` passes `-X ...version=dev`, so `versionLine` substitutes the Go pseudo-version, giving `spillway v1.0.1-0.20261019021435-a9054c29d6e2+dirty`: a v1.0.1 that never existed, for a build containing v1.1 work.
- Nothing in `spillway version`, `serve` output or the dashboard says which executable is running or whether the dashboard assets are the Preact build or the fallback.

### Client app and spillover observations

- The README quickstart sends `mock/echo` directly, which bypasses tiers, so a first-time user never sees spillover.
- The shipped `examples/config.mock.yaml` (also in every release archive) already defines `tiers.demo: [mock/rate-limited, mock/unavailable, mock/echo]` and fixed fake local keys, which demonstrates spillover offline.
- The only client example is one sentence in the README and one `curl .../v1/models` block in the dashboard; there is no Python, Node, PowerShell or environment-variable example.

### What already works

Verified on the `77e266b` binary: unknown-command suggestion, distinct missing default and explicit config hints, missing-variable naming, redacted `check`, `init` key safety and non-overwrite, chat-only key receiving `permission_denied` on `/api/providers`, dashboard key receiving provider status without secrets, `auto` returning `x-spillway-route: auto; tier free; candidate 1/1`, and an OpenAI-shaped `model_not_found` that names `GET /v1/models`.
All eight v1.1 tickets have checked acceptance criteria, browser tests cover both dashboard builds, and axe checks run in light, dark and narrow views.

- Account stacking, account rotation, key pooling or anything that evades a provider limit. Spillover stays across configured providers.

## Design

### Release line

Recommended: cut `release/v1.1` from `77e266b` and land every ticket there through pull requests (CI already runs on `pull_request`).
Tag `v1.1.0-rc.N` and `v1.1.0` on that branch; the release workflow runs on tag push from any commit.
After publication, merge `release/v1.1` into `main` and resolve the expected conflicts with `9dd80af` in the dashboard sources and `internal/api`.
This keeps v1.2 work out of a release-named branch (AGENTS.md), leaves shared `main` history untouched, and does not block the `spillway-v12` worktree.

Rejected: reverting `9dd80af` on `main`, releasing, then reverting the revert. It keeps one trunk but churns shared history and blocks v1.2 for the length of the release.
Rejected: shipping `9dd80af` in v1.1.0. It freezes an unfinished dashboard API and a store migration under ADR 0015.

### Version identity (new ADR 0024)

- Archive and image binaries report `vX.Y.Z` like `go install` does: GoReleaser ldflags use `v{{ .Version }}`, so `spillway version` prints `spillway v1.1.0 commit ...` on every channel.
  Snapshots print `v1.1.0-SNAPSHOT-<sha>`.
- `make build` sets `VERSION` from `git describe --tags --always --dirty`, so a local build reports, for example, `v1.0.0-12-g9dd80af-dirty` instead of a fictional pseudo-version.
  A plain `go build` without VCS data still reports `dev`.
- `spillway version` keeps its single line unchanged for scripts.
  A new `-verbose` flag adds the executable path, module path and version, VCS settings and dashboard assets (`embedded` or `fallback`), one `key: value` per line.
- `serve` logs one startup line with version, executable path and absolute config path before listening.
- A new authenticated `GET /api/gateway` returns `{"version": "v1.1.0", "dashboard_assets": "embedded"}` and nothing else.
  It follows every `/api/*` rule: dashboard key, Host check, `no-store`, OpenAI-shaped errors, no secrets, no config values.
  Both dashboards show "Connected to Spillway v1.1.0" so a user can see an older server is still answering.
- The install guide gains an "Upgrade and find older copies" section: `Get-Command spillway -All` on PowerShell, `which -a spillway` on POSIX, compare with `spillway version -verbose`.

Rejected: appending the executable path to the default `version` line; scripts that split the line would change.
Superseded by plan 0010: `spillway doctor` covers checks that `check` and `version -verbose` cannot make, such as variables set outside the current terminal and a port held by another program.

### CLI help and recovery

All changes keep command names, flags, exit codes 0/1/2 and secret handling.
Message wording is not stable under ADR 0015, so it may change; error `type` and `code` values are untouched.

- Root help: keep the quick start, add the offline path (`spillway init -yes -providers mock -store`), keep the command groups "Get started", "Tools" and "Experimental", restore the informative short descriptions, use lowercase descriptions for `completion` and `help`, and add one line: "Flags accept one or two dashes: -config or --config."
- Unknown command: print the suggestion and `Run 'spillway --help' to list commands.`, not the full usage. Exit code stays 2.
- `init` with an existing config: `config.yaml already exists; init never overwrites a config. Validate it with spillway check -config config.yaml, or create another with spillway init -config <new-path>.`
- Missing environment variable: keep the field and variable names, then show the history-safe, shell-appropriate command from the helper shared with plan 0010 C5 (`$env:GROQ_API_KEY = [Net.NetworkCredential]::new('', (Read-Host -AsSecureString 'provider key')).Password` on PowerShell, `read -rs GROQ_API_KEY && export GROQ_API_KEY` on bash and zsh). No hint puts a key value or a placeholder for one in command arguments or shell history.
- Listen conflict: name the address, say another process (possibly an older Spillway) is using it, show `server.listen: "127.0.0.1:8787"` as an example, and say client apps must use the same port.
- Newer store schema: say the database was written by a newer Spillway, name both schema versions and this binary's version, and suggest running that newer version or pointing `store.path` at a new file. Never suggest deleting the database.
- `check` success: after `config OK`, print the next command, `spillway serve -config <path>`.
- `init` success: numbered next steps naming the `default` local key for client apps and the `dashboard` key (when `-store`), each provider variable with its set/not-set state and the shell command when unset, the base URL, the `auto` model, and the client examples guide.
- `serve` startup: one summary that says whether a dashboard key is configured, whether the store is enabled, and the API, models and dashboard URLs. No key value is ever printed.

Rejected: an `init -listen` flag. The recovery hint covers the occupied-port case without a new stable flag.

### Client examples

- A new `docs/clients.md` and `examples/clients/` hold one canonical set: curl (POSIX), curl (PowerShell), Python `openai`, Node `openai`, and the SDK environment variables `OPENAI_BASE_URL=http://127.0.0.1:8080/v1` and `OPENAI_API_KEY=<LOCAL_APP_KEY>`.
- Every example uses model `auto`, the local endpoint, and the `<LOCAL_APP_KEY>` placeholder, and says to use the `default` key, not the dashboard key.
- The README quickstart switches its request to `auto` and adds "See spillover offline": serve `examples/config.mock.yaml`, send the documented request with its published fake key, and read `x-spillway-route: auto; tier demo; candidate 3/3`.
- The dashboard "Connect a client app" panel renders the same examples with the page origin substituted for `http://127.0.0.1:8080` and the placeholder kept. It never inserts the dashboard key or any key.

### Dashboard polish

Both dashboards get the same content.
The embedded Preact dashboard uses tabs and copy buttons; the fallback dashboard uses static `<details>` blocks so it needs no new script logic.
No new dependency is added.

- Gateway identity in the header from `GET /api/gateway`.
- Provider status: a short legend separating "configured" from "observed since this server started", cooldown end times as local time plus relative time, reason labels in plain words, and the last refresh time.
- Playground: default to `auto` or the first listed virtual model, explain under the model control that direct model references skip spillover, render exhaustion errors as a candidate list from the OpenAI error message, and offer "Copy as curl" with the placeholder key.
- Route explanation: for `candidate n/m`, show which candidate answered and that earlier ones were skipped or failed; link the terms cooldown, circuit breaker and exhaustion to short definitions taken from GLOSSARY.md. Unknown reasons stay verbatim. No routing logic moves into the browser.

### Fallback dashboard (amend ADR 0021 before it is committed)

`go install` cannot run the Vite build, so a binary built without the `dashboardassets` tag serves the checked-in fallback dashboard.
ADR 0021 will record that the fallback is a supported channel, must keep onboarding, provider status, playground and route explanation parity in content, follows the same CSP and key rules, and is covered by the same browser tests.

## ADR and glossary changes

- Commit ADRs 0019, 0020 and 0021 with plan 0007, reformatted to one sentence per line with a "What needs a new ADR" section like ADRs 0015 to 0017. Decisions are unchanged except the ADR 0021 fallback addition above.
- New ADR 0024, "Version identity across install channels": the `v`-prefixed archive version, `git describe` local builds, `version -verbose`, the `serve` startup identity line and `GET /api/gateway`. It amends the ldflags bullet of ADR 0016.
- GLOSSARY.md additions:
  - **Fallback dashboard**: the checked-in dashboard served by a binary built without the embedded Preact assets, such as one from `go install`. _Avoid_: legacy dashboard.
  - **Client example**: a copyable snippet that configures a client app with the local endpoint and a local key placeholder, never a real key. _Avoid_: SDK sample, integration.

## Hard-rule check

- No quota evasion: no ticket touches provider selection; spillover remains across configured providers and is only explained and demonstrated.
- No credential collection: no prompt for or storage of any key; examples use placeholders.
- Secrets never leak: every new output (`version -verbose`, startup summary, recovery hints, `/api/gateway`, examples) has a canary test proving local and provider keys are absent.
- Single binary, no cgo: no new Go or frontend dependency; `CGO_ENABLED=0 go build ./...` stays in `make lint`; the fallback dashboard keeps `go install` working without Node.
- Local by default: no listen default changes; the listen hint suggests another loopback port only; `/api/gateway` keeps key and Host checks.
- OpenAI compatibility: no `/v1/*` change; dashboard behavior reads existing headers and error shapes.
