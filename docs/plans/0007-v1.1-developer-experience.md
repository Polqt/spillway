## Goal

Make Spillway easier for first-time developers to install, configure, start and understand without repeatedly consulting the README, while preserving the v1.0 compatibility promise, single-binary distribution, local-first operation and BYOK security model.

This is a planning document. It does not authorize implementation. T19, the independent live routing evaluation, remains separate and is not a dependency or acceptance gate for this milestone.

## Current-state assessment

The assessment is based on the released `v1.0.0` source. The current worktree has no code changes relative to that tag; its only later tracked difference is an edit to the v1.0 release plan. A pre-existing deletion of `.github/dependabot.yml` was present during planning and is unrelated.

### CLI and first run

- `internal/cli` uses Go's `flag` package and a small explicit command switch. This keeps the binary dependency-light and preserves controlled exit codes, but help is one flat command list. There is no `help <command>`, examples, command-specific usage page, or shell completion.
- `serve`, `check`, `catalog` and `init` have useful `-config` flags and contextual validation, but most operational errors end at the failing operation. Missing default config points to `spillway init`; there is no consistent recovery hint for missing environment variables, invalid config fields, occupied listen addresses or disabled dashboard storage.
- `init` is already a substantive first-run wizard: it chooses providers, asks for explicit free-tier attestation, optionally enables the store/dashboard, generates a private local key, writes provider environment references only, validates before writing, refuses overwrite, and supports non-interactive flags. It never calls the network. Do not replace this behavior or add provider-key prompts.
- The README and install guide provide offline and real-provider quickstarts. A next-step path is present after `init`, but the resulting experience still asks users to copy local keys from a private config and consult docs for client setup and the dashboard.
- Existing tests cover command dispatch, exit codes, redaction, init combinations, cancellation, file permissions and an end-to-end mock quickstart. Additive help and diagnostics should be tested through `cli.Run` and the binary-level smoke path.

### Dashboard and API

- The dashboard is three local assets (`dashboard.html`, `dashboard.css`, `dashboard.js`) embedded by `go:embed`; it needs no runtime or build-time Node installation.
- The current dashboard provides budget, usage totals, recent decisions, cooldowns and manual refresh. It is a useful read-only operations view, not an onboarding flow or request workbench.
- `/dashboard` serves a data-free shell. `/api/*` requires a local key marked `dashboard: true`, is bounded, returns OpenAI-shaped errors and `Cache-Control: no-store`. The page keeps the entered key in `sessionStorage` and sends it in a bearer header.
- ADR 0012 makes the CSP, no-inline-script rule, same-origin-only assets, `textContent` rendering and key/session behavior part of the security design. Browser responses must not contain provider credentials, and prompt/response data must not be added to persistent storage or logs.
- Tests verify asset embedding, CSP/security headers, no external resources, safe DOM rendering patterns, dashboard access, Host checks, response shapes and secret non-disclosure. They do not yet establish keyboard/screen-reader accessibility, responsive behavior, or browser flows.
- There is no provider-status endpoint. Existing quota snapshots describe runtime cooldown/breaker observations, not current provider reachability or a guarantee that a request will succeed. The playground should use the existing authenticated `/v1/chat/completions` contract and explain actual returned route metadata instead of creating a second routing implementation.

### Compatibility and architecture constraints

- ADR 0015 treats stable CLI names, flags, exit codes, API shapes, dashboard API field meaning, routing headers and config behavior as compatibility commitments. New help text and commands can be additive; existing command and flag behavior must remain.
- ADRs 0003, 0012 and 0017 constrain local-key access, the browser security boundary and init secret handling. ADR 0004 keeps the dashboard embedded under `apps/spillway/web` and tests under `tests/`.
- `CONTEXT.md` and coding standards prefer the standard library, `net/http`, no cgo and exported-API behavior tests. Release assets are already embedded in the Go executable; v1.1 must preserve offline startup and must not require Node for users.

## Architecture recommendation

### CLI

Adopt Cobra for command dispatch, help, command discovery and shell completion, while retaining the existing command functions behind small adapters. Preserve stable command names, flags, injected I/O and exit codes. Use Huh for the interactive `init` path while retaining the existing flag-driven and `-yes` behavior for automation. Use Lip Gloss for restrained terminal hierarchy and color, with plain output when redirected or color is unavailable.

| Option | Value | Cost / concern | Recommendation |
| --- | --- | --- | --- |
| Existing dispatcher + standard library | No runtime dependency, direct control over exit codes and streams, minimal migration | Help, suggestion and completion behavior must be maintained locally | Keep existing command functions and `cli.Run` as the test seam; replace only dispatch/help with Cobra. |
| Cobra | Automatic command help, unknown-command suggestions, nested commands and generated shell completion | Adds Cobra/pflag and a command-tree migration; must preserve injected readers/writers, version wiring, exit codes, stable flags and experimental command labeling | Adopt for v1.1 command discovery and help. |
| Charm Huh | Interactive select/multi-step forms and a documented accessible mode | Adds a terminal UI dependency and an alternate interactive behavior to test; existing `init` behavior is already covered by compatibility/security tests | Adopt for interactive `init` only; retain flags and `-yes` for automation. |
| Lip Gloss | Rich terminal styling | Presentation-only dependency and more terminal edge cases; styling must not affect diagnostics or machine-readable output | Adopt restrained styling for help and status output; disable color for redirected output or unavailable color support. |

Proposed examples:

```text
spillway --help
spillway help init
spillway init -yes -providers mock -store
spillway check
spillway serve
spillway catalog -config ./config.yaml
```

Help should identify the quick path (`init`, `check`, `serve`, open `http://127.0.0.1:8080/dashboard` when store/dashboard access was enabled), distinguish experimental evaluation commands, and show `-config` consistently. Errors should state the failing command/config field and one safe next action. Diagnostics must never echo key values or upstream response bodies.

### Web architecture

Adopt Preact with Vite for the expanded dashboard flows. Keep the same-origin security model, existing JSON APIs and authenticated OpenAI chat endpoint. Pin the frontend toolchain and build production assets in development/CI; embed those assets in the released Go binary so users need no Node runtime.

| Option | Value | Cost / concern | Recommendation |
| --- | --- | --- | --- |
| Existing HTML/CSS/vanilla JS + Go embed | No frontend runtime/build dependency; matches shipped assets, CSP, deployment and current test seams | UI state and DOM updates remain hand-written | Retain only if neither evaluated library provides enough value to justify its maintenance cost. |
| Go templates + vendored HTMX | Server-driven fragments can reduce custom DOM rendering and keep simple forms progressive | Requires a vendored local HTMX asset; bearer-key handling and streaming playground behavior still need custom JavaScript; fragment routes add API/UI coupling | Rejected for v1.1 because it leaves substantial client-side interaction code while adding a second rendering model. |
| Preact + Vite | Components and a shared state model fit onboarding, status, existing dashboard views and the streaming request playground; Vite emits static assets for Go to embed | Adds Node/pnpm development and CI steps, a lockfile, build artifacts and browser-test tooling; users still run only the Go binary | Adopt for v1.1 because the dashboard becomes a stateful multi-flow app; keep Node build-time only. |

No external CDN, font, script, telemetry, hosted backend or mandatory Node runtime is allowed. If a future decision adopts a frontend build tool, CI must build deterministic static assets and the release binary must continue to embed them.

### UI and data boundaries

- Keep a small token set in CSS custom properties for color, spacing, type scale, radius, borders, focus rings and motion. Reuse existing light/dark color-scheme support and use semantic HTML and native controls.
- The dashboard key continues to be entered by the user and sent only as an Authorization header to same-origin local endpoints. Do not put keys in URLs, HTML, logs or API response bodies. Keep `sessionStorage` behavior explicit with a visible disconnect/forget action.
- Add only a safe dashboard summary endpoint if existing `/api/quotas`, `/api/budget` and authenticated config state cannot provide the needed states. It may report provider name, configured/credential-present state, and observed cooldown/breaker state; it must not report key values, environment values, provider URLs or claim current reachability.
- Do not probe providers for status. Provider status is limited to local configuration and observed runtime signals; a request through the playground is the user's explicit way to exercise a configured route.
- The playground sends a user-entered OpenAI-compatible chat request through the same `/v1/chat/completions` handler with the selected configured model. Allow any configured model; warn before submission that real providers receive the request and may charge for it. Show a cost estimate only when configured pricing supports one. Do not persist or log playground prompts/responses. Support cancellation and display streaming output incrementally; surface `x-spillway-provider`, `x-spillway-model`, `x-spillway-route` and cache headers as actual response metadata.
- Routing explanation is descriptive, derived from actual route headers and stored decision fields. It must not predict routing with separate frontend logic or include prompt text in telemetry/history.
- Any additive `/api/*` field or endpoint keeps key authorization, Host protection, bounded input, OpenAI error shape and `no-store`. Keep existing field names and meanings unchanged.

## User journeys and screen flows

### CLI first run

1. `spillway --help` presents a short purpose statement, stable command groups, one mock quickstart and links/URLs users can open locally.
2. `spillway init` keeps the existing provider, attestation and store choices. It states defaults and safety implications before writing.
3. Completion reports config path, provider environment-variable names and whether each variable is set, without values; it reports dashboard enablement and the exact next commands.
4. `spillway check` reports success or names the invalid field/environment variable and next action, while redacting secrets.
5. `spillway serve` reports the listen address, authenticated API base URL, dashboard URL and whether dashboard data access is configured. It does not print any local or provider key.
6. If the default config is absent, `serve`/`check` say `spillway init` is the next step. If another config path was requested and is absent, guidance includes that path and a matching `init -config` example.

### Dashboard onboarding and status

1. User opens `/dashboard`; a welcome/setup state explains that dashboard APIs require a local key marked `dashboard: true`, while `store:` is optional and enables usage history.
2. User enters the dashboard key. It is sent to same-origin APIs only; the UI provides a clear disconnect/forget action and handles 401/403 with a specific config hint.
3. Onboarding shows config-readiness facts, provider names and credential-presence state, and clearly separates “configured” from observed runtime signals. If there is no recorded traffic or store, it offers the playground and a copyable local client example without exposing keys; history panels explain that `store:` enables persistence.
4. When traffic exists, the home view links recent usage, budget and cooldown information with routing explanations.

### Request playground and routing explanation

1. User chooses a configured model or virtual model from a bounded list and enters messages/options.
2. The page shows that a request is sent to the configured provider and may incur cost when applicable, submits only on user action, and allows cancellation.
3. Streaming output appears as chunks arrive. Errors follow OpenAI-compatible display rules and are redacted by the server contract.
4. A result summary shows the actual provider, model, route reason, cache state and any spillover/skips returned by the existing API/store. A separate explanation maps known route reason markers to plain language; unknown markers remain visible verbatim.
5. The user can copy an SDK/curl snippet with placeholders for the local key. The page never reads config files or offers to reveal a key.

## CLI examples and error guidance

```text
spillway help serve
spillway init -yes -providers mock -store -config ./config.yaml
spillway check -config ./config.yaml
spillway serve -config ./config.yaml
```

Representative recoveries:

- Missing default config: `Run spillway init to create config.yaml.`
- Missing named config: `No config at ./config.yaml. Create it with spillway init -config ./config.yaml.`
- Missing provider environment variable: identify the variable name, provider and the need to set it in this process environment, without displaying a value.
- Existing destination during init: identify the path and explain that init does not overwrite; suggest choosing a new path.
- Dashboard returns 403: explain that the entered local key needs `dashboard: true`; distinguish this from server/store being disabled.
- Listen failure: identify address and likely occupied-port remediation; do not suggest changing loopback defaults or disabling local-key requirements.

## Milestones and tickets

### M1: CLI onboarding

**T01 - Add Cobra command discovery and styled help**

- **Blocked by:** None.
- **What it delivers:** Users can discover commands, understand the quick path, get command-specific examples, and generate shell completion.
- **Acceptance:** Cobra preserves stable commands, flags, and exit codes; unknown commands suggest valid commands; Lip Gloss styles help/status output but turns color off when redirected or unavailable; tests retain `cli.Run` coverage.

**T02 - Make interactive init accessible with Huh**

- **Blocked by:** None.
- **What it delivers:** First-time users can choose providers and setup options through an accessible interactive flow while scripts keep the existing flag-based flow.
- **Acceptance:** Huh is used only for interactive input; existing flags and `-yes` remain supported; provider attestation and optional-store behavior are preserved; setup never reads or writes provider key values; generated config remains valid and non-overwriting.

**T03 - Explain CLI failures and next steps**

- **Blocked by:** T01.
- **What it delivers:** Users receive a safe, actionable recovery step for common setup/configuration failures and clear next steps after successful init and startup.
- **Acceptance:** Missing default and explicit config paths have distinct guidance; missing environment variables and listen errors name the safe next action; init and serve identify relevant API/dashboard next steps; no secret or upstream body is printed; existing exit codes remain.

### M2: Embedded dashboard onboarding and status

**T04 - Ship an accessible Preact dashboard shell and onboarding**

- **Blocked by:** None.
- **What it delivers:** Users can open an embedded, responsive dashboard that explains dashboard-key access, optional usage storage, privacy and the next useful action.
- **Acceptance:** Preact/Vite builds deterministic same-origin assets embedded in Spillway; users need no Node runtime; dashboard-key bearer handling and forget action preserve ADR 0012; onboarding works without `store:` when a dashboard key is configured; history explains that storage is optional; keyboard/screen-reader access and narrow layouts work.

**T05 - Show safe provider and gateway status**

- **Blocked by:** T04.
- **What it delivers:** Users can distinguish configured providers and credential presence from observed runtime cooldowns or failures.
- **Acceptance:** Status does not claim live reachability and causes no provider probes; responses contain no secret, environment value, provider URL or authorization header; API access remains dashboard-key protected, bounded and `no-store`; missing-store and empty-history states are clear.

### M3: Request playground and routing explanations

**T06 - Submit and inspect requests in the playground**

- **Blocked by:** T04.
- **What it delivers:** Users can explicitly send a streaming or non-streaming request through Spillway to any configured model and inspect its result.
- **Acceptance:** The playground uses existing `/v1/models` and `/v1/chat/completions` behavior; warns that a configured provider receives the request and cost may apply; shows cost estimates only when configured pricing supports them; supports cancellation and errors; prompts/responses are not logged or persisted; keyboard/screen-reader flows work.

**T07 - Explain actual routing decisions**

- **Blocked by:** T06.
- **What it delivers:** Users can understand the selected provider/model, route reason, cache state and observed skips for a playground request and recent decisions.
- **Acceptance:** Explanations use actual response headers and stored metadata, never a separate routing implementation; unknown route reasons remain visible; prompt content is not included; existing route grammar and API field meanings remain unchanged.

### M4: Release-ready integration

**T08 - Verify compatibility, accessibility and binary delivery**

- **Blocked by:** T03, T05, T07.
- **What it delivers:** Users receive the complete v1.1 experience from a verified single binary with concise setup and operating guidance.
- **Acceptance:** Historical configs and stable `/v1/*` and `/api/*` contracts remain compatible; assets build deterministically and are embedded; no CDN, telemetry, cgo or user-side Node runtime is required; automated and manual accessibility/responsive checks pass; README/install docs cover the self-guided path; Go checks and clean-binary mock smoke pass; T19 does not block release.

## Test strategy

- **CLI unit behavior:** Test `cli.Run` output/exit codes via injected stdin/stdout/stderr. Cover root and per-command help, misspelled command, malformed flags, recovery hint selection, no-secret output, and success next steps. Keep tests in `tests/cli/`.
- **CLI black-box behavior:** Extend the existing binary/e2e flow for `init -> check -> serve`, verify startup guidance and mock API access using a temporary config and ephemeral port, and assert captured output contains no local/provider key.
- **Dashboard delivery/security:** Extend `tests/web/` and `tests/api/dashboard_test.go` for embedded routes, CSP, no external assets, no-store, Host/auth rules, bounds, error shape and absence of provider credentials/config values.
- **Dashboard behavior:** Add browser-level tests for onboarding, 401/403, no-store/error state, streamed mock response, cancellation, routing details, keyboard order/focus visibility and small-screen layout. Prefer testing user-visible behavior over selectors or implementation structure.
- **Compatibility:** Preserve historical config fixtures and existing API/route grammar assertions. Verify existing dashboard API fields and error type/code values remain unchanged.
- **Security:** Include canary fake provider/local keys and prompt markers in fixtures; assert they do not appear in HTML, browser-visible status payloads, CLI output, logs or persisted usage rows. Dashboard status must never expose provider base URLs or authorization headers.
- **Build/release:** Verify embedded production assets are present in the built single binary and no Node process/runtime is needed to run it. If a build step is ever adopted, CI must build and embed assets from a clean checkout and fail on stale output.

## Accessibility and responsive acceptance

- All functionality is keyboard operable with visible focus, logical focus order, no keyboard traps, and a skip link or equivalent landmark navigation.
- Inputs have persistent labels and concise instructions; validation and request errors are associated with their controls and announced through an appropriate live region.
- Status is not conveyed by color alone; text/icon labels remain meaningful in light and dark color schemes.
- Semantic landmarks/headings, accessible names, table/list structures and status announcements are checked with an automated accessibility scan plus manual keyboard and screen-reader review.
- Text and controls remain readable and usable at 320 CSS px width and at 200% zoom; no horizontal scrolling is needed for primary flows.
- Respect `prefers-reduced-motion`; focus indicators and contrast meet WCAG 2.2 AA targets.

- All approved ticket acceptance criteria are satisfied, with no change to default routing or stable API/config behavior.
- `make check`, `make build`, and `CGO_ENABLED=0 go build ./...` pass. The v1.1 release check runs only after approval and follows existing release gates.
- Mock onboarding and playground work offline after installation; requests to configured providers are made only when the user submits a request.
- Production dashboard assets are embedded in the released binary; there is no CDN, telemetry, mandatory Node runtime for users, cgo or new cloud service.
- Secrets and prompt/response content are absent from logs, errors, status responses and persistent dashboard storage.
- Automated checks and manual accessibility/responsive QA pass; docs explain the short path and material privacy/spend choices.
